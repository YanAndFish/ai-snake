# AI 响应延迟下的路线调度

本次 5 个标准难度种子的真实 API 试验中，完整路线方案的 90 秒得分中位数为 210，单步基线为 40。五组配对全部增分，配对中位增分为 160。满窗口存活从 4/5 增至 5/5。只有种子 201 延长了观察到的存活时间，其他四对都存活到窗口结束。

完整与精简提示词未分胜负，按预先规则使用完整版本。这个结果支持本次整套路线方案的工程选择。它无法单独衡量模型选择相对本地规则的收益。

## 真实 API 比较方法

2026-11-05 使用 `gpt-6-luna` 和 `https://api.openai.com/v1/decisions`。Chrome 版本为 `157.0.8103.39`。`scripts/evaluate-live.mjs` 使用 Chrome 原生 fetch，以及待测源码中的 session、transport、controller 和 parser。游戏由真实 rAF 按 60 Hz 推进，请求期间照常移动。

每局只有一次生命。死亡后分数冻结，计分窗口照常走完。每轮最多两页，每局最多一个在飞请求。每局先计算成功解析请求的 P50、P90，再汇总五局结果。取消与未完成请求不进入成功延迟统计。

| 方案 | 调度与执行 | 模型收到的信息 |
|---|---|---|
| A 单步基线 | AI 固定速度，旧单步调度，等待期间直行 | 当前棋盘、延迟场景与单步选项 |
| B 完整路线 | 从未来起点提前请求连续路线，等待期间执行本地避险 | 未来棋盘、身体坐标、各路线动作与结果 |
| C 精简路线 | 与 B 使用相同代码和候选生成方式 | 从 B 请求中删除身体坐标和逐步动作 |

C 同时删除 `input` 和选项说明中的 `Body`、`moves`。它保留未来起点、已知食物、`length`、`safe_extension`、`eatAt`、`progress` 和终点。B 与 C 只比较发送给模型的信息。A 与 B 的差异包含调度、本地路线生成、等待避险和提示词。

标准难度使用种子 201 至 205，每局 90 秒，AI 移动间隔固定为 10 tick。15 局按固定的 8 轮交错运行。预设选型要求候选至少赢 4 个种子，配对中位增分至少 10 分，总分更高，且中位增分大于差值四分位距。满窗口存活数和配对中位存活差也不能回退。四分位数使用线性插值 type 7。这些规则用于工程选择，不是统计显著性的证明。

| 401 | 30 | 250 | 49.084 | 90 |

两对都没有出现得分或存活回退。A、B 的满窗口存活分别为 0/2 和 2/2。这部分只描述两个疾速种子的结果，不独立选优，也不能代表疾速的全部棋盘。

四局均通过运行检查，源码 hash 与标准难度相同。A 发出 140 个请求，138 个 HTTP 200 完成解析，2 个因死亡取消。B 发出 137 个请求，136 个 HTTP 200 完成解析，1 个在窗口结束时取消。HTTP、网络和解析错误均为 0，清理后在途请求为 0。原生 fetch 并发峰值为 1，时钟比值为 0.9990 至 0.9999，最大采样间隔为 28.4 ms。

B 的模型所选路线执行 1263 步、吃到 50 个食物。等待避险执行 70 步、吃到 1 个，唯一候选执行 16 步。脚本移动和起点不匹配均为 0，迟到响应为 2。两轮正式试验共发出 1669 次真实 POST，未超过预设的 2500 次上限。

B 的模型所选路线占实际移动的 95.0%，吃食的 96.1%。C 对应为 95.1% 和 99.0%。所有候选路线都由本地生成，模型只选择其中一条。`apiMoves` 和 `apiEats` 包含本地规划的作用，不能称为模型逐步规划或模型的净贡献。

B、C 各局都有真实响应完成解析并进入路线执行。移动来源之和等于实际移动数，吃食来源之和等于最终吃食数，脚本移动为 0。A 缺少移动来源统计，相关字段为 `null`。脚本没有逐请求的首次执行时间，因此请求应用数和应用率也为 `null`。

只读比较模型选择和简单排序规则时，B 一致 247/312 次，C 一致 274/313 次。规则按吃到已知食物、较早吃到、较大 `progress` 和候选顺序排序。一致率只说明选择是否不同，无法推导换用这个规则后的最终分数。

## 调度方式

会话执行已确定的前缀，同时从前缀终点请求下一条路线。请求使用 `SNAKE/3 ROUTES`。`U`、`D`、`L`、`R` 标记各路线的首方向，选择值代表整条路线。早到响应等待起点，到达起点后核对完整棋盘再执行，晚到响应丢弃。冷启动和迟到时执行本地避险，唯一候选直接在本地执行。

最近 8 次成功延迟的 P90 不超过一次移动时间时使用 1 步。超过时使用 `ceil(P90 / 一次移动时间) + 2`，限制为 8 至 32 步。没有样本时使用 16 步。每个候选至少模拟 16 步。挂起请求没有自动超时，可通过暂停或停止 AI 取消。

## 用模拟检查调度机制

模拟使用固定选择器和注入延迟，没有真实 Key 或真实 API 请求。它用于检查调度和执行，不参与本次提示词选型。汇总单独保存在 [模拟结果 JSON](ai-latency-results.json)。

双方 AI 都固定速度。每局固定推进 3600 tick，即 60 游戏秒。主矩阵使用种子 1 至 12，延迟为 100、600、1200 ms 和 `[100,300,1200,600]`。独立矩阵使用种子 101 至 112，延迟为 240、900、1800 ms 和 `[100,100,300,100,1800,100,900,3600]`。两组都运行 `normal`、`fast`，以及 `food`、`first` 选择器，每个矩阵 192 局。

下表为 `food` 选择器结果，每行各 48 局。它优先选择较早吃到已知食物的路线，再比较距离缩短量。`first` 选择第一个候选。

| 矩阵 | 难度 | 单步基线均分 | 路线均分 | 基线存活 | 路线存活 |
|---|---|---:|---:|---:|---:|
| 主矩阵 | 标准 | 64.38 | 147.50 | 13/48 | 48/48 |
| 主矩阵 | 疾速 | 72.29 | 180.42 | 6/48 | 48/48 |
| 独立矩阵 | 标准 | 4.38 | 114.79 | 5/48 | 48/48 |
| 独立矩阵 | 疾速 | 3.75 | 134.17 | 5/48 | 48/48 |

路线方案的 384 局模拟全部存活，错误与约束失败为 0，请求最大并发为 1。100 ms 下，它的 `food` 均分低于单步基线，标准难度的基线与路线分别为 250.8 和 205.8，疾速分别为 282.5 和 256.7，存活分别由 9/12、6/12 变为 12/12。这说明得分收益取决于延迟场景，不能用整矩阵平均值声称处处更好。

另有 8 个无头 Chrome 延迟注入场景，使用种子 83、两种难度和主矩阵的四组延迟，每局 12 秒。全部存活并通过运行检查。时钟比值为 0.9922 至 0.9997。它们使用真实 rAF、生产传输层和解析器，响应由固定选择器生成。

模拟复现命令与场景格式见 [测试说明](testing.md#用真实时钟模拟响应延迟)。

## 证据范围

真实结果只覆盖本次一个模型、五个标准难度种子和固定 90 秒窗口。满窗口存活是截断观察。候选检查的步数有限，本地避险也可能遇到死路，不能据此推断所有棋盘或无限存活。

A 与 B 比较整套方案。要衡量模型相对简单规则的收益，需要在相同调度下增加非模型选择对照。成功延迟也没有包含取消或未完成请求，必须与请求结果一起阅读。

可移植的真实分组、逐局与配对数据见 [真实结果 JSON](ai-live-results.json)。大体积请求与采样保存在本次临时目录，不写入仓库。完整脚本用法与精确基线复现步骤见 [真实 API 运行说明](evaluate-live.md)。
